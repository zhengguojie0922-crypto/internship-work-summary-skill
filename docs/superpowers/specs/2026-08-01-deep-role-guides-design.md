# 岗位规则深度扩展设计

日期：2026-08-01

## 背景

`summarizing-internship-work` 已支持前端、后端、客户端、测试、DevOps、数据分析和算法七类目标岗位，但当前岗位参考文件主要由简短清单组成。它们能够完成岗位路由，却不足以稳定指导以下工作：

- 从岗位视角深入追踪代码链路；
- 识别真实技术决策、约束、取舍和失败模式；
- 判断一项实现的技术深度与个人归属边界；
- 将证据转换为有岗位区分度的简历和面试材料；
- 生成与实际代码证据相连的追问和场景题。

## 目标

建立“通用深度分析框架 + 七个岗位专属指南”的两层规则体系，使 Skill 能够先按岗位深挖代码证据，再把证据映射为简历表述、面试介绍、问题树和场景题。

本次改动必须保持以下现有契约不变：

- 指定功能路线不询问 Git 身份；
- Git 发现路线确认 Git 身份和目标岗位；
- 整个过程最多两轮确认；
- 目标仓库分析保持只读；
- 不执行目标仓库代码，不安装依赖，不切换分支，不 fetch；
- 唯一运行时文件仍是 `career-output/实习产出与面试准备.md`；
- 不创建任何运行时中间文档或目录；
- 不编造指标、业务结果、所有权、因果关系或运行时行为。

## 方案选择

### 方案一：七个岗位文件独立完整扩写

优点是单文件阅读直接。缺点是通用分析方法会在七个文件中重复，容易产生规则漂移，并增加上下文占用。

### 方案二：通用框架与岗位专属指南分层

新增通用岗位分析框架，七个岗位文件只承载岗位特有的代码链路、决策、风险、指标和面试维度。该方案兼顾分析深度、渐进加载和维护一致性。

### 方案三：每个岗位拆成代码、简历和面试三个文件

优点是主题最细。缺点是文件数量超过二十个，路由和加载复杂度明显增加，不符合当前 Skill 的规模。

采用方案二。

## 文件架构

新增：

- `skills/summarizing-internship-work/references/role-analysis-framework.md`

修改：

- `skills/summarizing-internship-work/SKILL.md`
- `skills/summarizing-internship-work/references/role-classification.md`
- 七个 `role-*.md` 岗位指南
- `tests/test_skill_contract.py`

加载顺序：

```text
SKILL.md
  -> role-classification.md
  -> role-analysis-framework.md
  -> 一个主岗位指南
  -> 必要时最多一个辅助岗位指南
  -> resume-writing.md / interview-expansion.md
  -> career-output/实习产出与面试准备.md
```

Skill 不一次加载全部岗位指南。目标岗位明确后，必须读取通用框架和主岗位指南。只有代码证据确实跨越岗位边界且辅助视角与目标岗位相关时，才读取一个辅助岗位指南。

## 通用岗位分析框架

`role-analysis-framework.md` 统一规定以下分析过程：

1. 建立入口、边界、核心逻辑、数据流、状态或持久化、依赖、配置、异常和测试证据链。
2. 对关键实现识别约束、备选方案、实际选择、可观察取舍、失败模式和验证证据。
3. 将技术深度分为基础实现、独立负责、复杂问题解决和系统级改进四级；级别只由证据决定。
4. 区分代码事实、Git 归属、用户陈述、静态推断和未知项。
5. 决定一条证据适合进入简历、面试补充、待确认指标还是未知项。
6. 从实际证据生成基础原理、实现细节、方案取舍、故障定位、扩展设计和场景题问题树。

框架只提供跨岗位方法，不重复七个岗位的技术知识。

## 岗位指南结构

七个岗位指南使用相同的十部分结构，但内容必须体现岗位差异：

1. `Role Boundary and Subdomains`：岗位边界、子方向和相邻岗位边界。
2. `Entry-Point Discovery`：文件、框架结构、命名、配置和运行边界信号。
3. `Typical Code Chains`：按常见功能类型给出具体追踪路径。
4. `Technical Decision Matrix`：决策点、证据位置、可讨论取舍和禁止推断项。
5. `Failure Modes and Risks`：岗位特有的边界、安全、性能、可靠性或质量风险。
6. `Validation Evidence`：不同测试、监控、实验或校验能证明的范围。
7. `Impact and Metrics Evidence`：允许使用的指标来源和需要用户补充的指标。
8. `Resume Mapping`：保守版、标准版和影响力版表述所需证据。
9. `Interview Question Tree`：六类问题及岗位专属场景题方向。
10. `Overclaim Guardrails`：常见错误归属、无证据结论和降级写法。

每个岗位指南目标长度约为 120 至 180 行。内容应是可执行的分析规则和紧凑矩阵，不写通用技术百科，不预置脱离仓库证据的固定答案。

## 七个岗位的专属重点

- 前端：页面与组件边界、状态一致性、请求竞态、渲染性能、可访问性、埋点和端到端体验。
- 后端：API 契约、领域边界、事务一致性、幂等、并发、缓存、消息、权限和可观测性。
- 客户端：生命周期、状态同步、网络与本地存储、离线与弱网、线程、资源、平台适配和发布稳定性。
- 测试：风险建模、测试分层、fixture、隔离性、稳定性、覆盖边界、缺陷定位和发布门禁。
- DevOps：构建发布链、环境一致性、制品、部署策略、回滚、权限、可观测性和故障恢复。
- 数据分析：采集、清洗、SQL、指标口径、数据模型、质量校验、实验解释和可视化决策。
- 算法：数据与标签、特征、训练、评估、基线、实验、推理、漂移、性能和工程化边界。

## 路由与跨岗位处理

目标岗位仍是必需输入。Skill 先选择主岗位，再加载对应指南。

当功能跨岗位时：

- 最终输出围绕目标岗位组织；
- 辅助岗位证据只解释依赖、接口或协作边界；
- 不把调用其他系统等同于负责其他系统；
- 不把团队结果自动归属为个人结果；
- 辅助指南最多一个，防止上下文无界扩张。

目标岗位不属于七类时，选择最接近的主岗位指南，并在最终文档中明确映射理由和不适用边界。

## 证据不足与降级

- 链路中断时，停在最后一个有证据的节点，记录缺失关系和可验证方式。
- 无法证明技术方案由用户决定时，只描述实现、修改或参与，不使用“主导设计”。
- 没有运行数据时，不从静态代码推断性能、规模、增长、稳定性提升或业务结果。
- 只有低置信度推断时，不生成影响力版简历结论，将其放入未知项或待补充指标。
- 岗位指南中的问题模板必须由实际证据实例化；没有对应证据时不强行生成该方向的答案。

## 测试设计

采用轻量 TDD，不进行新的大规模模型前向测试。

先在 `tests/test_skill_contract.py` 增加失败的契约测试，验证：

- `SKILL.md` 明确要求读取通用岗位分析框架；
- `SKILL.md` 限制为一个主岗位指南和最多一个辅助指南；
- 七个岗位文件都包含统一的十个必需章节；
- 每个岗位指南包含其专属链路、决策、风险、验证、指标、简历和面试信号；
- 七个岗位指南不是仅替换岗位名称的重复文本；
- 原有两条路由、最多两轮确认、只读边界和单文档输出契约保持不变。

实现后运行：

```text
python -m unittest tests.test_skill_contract -v
python -m unittest discover -s tests -v
python -m compileall -q skills tests
git diff --check
```

## 非目标

- 不修改 Git 证据采集脚本的命令行接口；
- 不增加第八类岗位；
- 不增加外部依赖；
- 不创建示例输出、中间证据文件或运行时缓存；
- 不修改安装方式、Skill 名称、版本号或最终输出路径；
- 不承诺未经本轮测试验证的模型或平台行为。
