# Clean v1.0 Republishing Design

## Goal

Republish the current `Internship Work Summary Skill` under the current GitHub account as a new repository with one clean root commit and a `v1.0.0` release. The new repository must not inherit the previous repository's Git history or contributor attribution.

## Canonical Release Identity

- GitHub owner: `zhengguojie0922-crypto`
- Repository: `internship-work-summary-skill`
- Skill identifier: `summarizing-internship-work`
- Project display name: `Internship Work Summary Skill`
- Skill display name: `Internship Work Summary`
- Version file value: `1.0.0`
- Git tag: `v1.0.0`
- Root commit subject: `Initial release of Internship Work Summary Skill v1.0.0`
- Commit author and committer: `zhengguojie0922-crypto <zhengguojie0922@gmail.com>`

The email must remain verified on the current GitHub account so GitHub attributes the root commit to `zhengguojie0922-crypto`.

## Source Snapshot

Use the tracked file state from the current `main` branch after the completed Skill rename. Export tracked files only. Do not copy the source `.git` directory, linked worktrees, ignored files, `.superpowers` runtime state, temporary directories, Python bytecode, coverage output, editor configuration, or local environment files.

The clean repository keeps the current product source, role references, collector, public documentation, tests, CI workflow, license, contributing guide, and tracked historical design/plan documents. This migration changes release identity and repository history; it does not redesign Skill behavior or remove tracked project content.

## v1.0 Content Changes

Before creating the clean root commit:

- Change `skills/summarizing-internship-work/VERSION` from `0.3.0` to `1.0.0`.
- Update the README opening release text to describe `1.0.0` as the first stable release.
- Remove the `0.2.x` upgrade section because the new repository has no supported pre-1.0 installation lineage.
- Update publishing tests to require `1.0.0` and to stop requiring the removed migration section.
- Preserve installation commands, explicit invocation, two request routes, seven target roles, single-document output, safety constraints, and verification guidance.

## Repository Migration Sequence

Use a reversible sequence until the new repository is proven usable:

1. Verify the source `main` branch and the v1.0 content changes locally.
2. Rename the existing GitHub repository to `internship-work-summary-skill-legacy`.
3. Create a new public GitHub repository named `internship-work-summary-skill` without a generated README, license, `.gitignore`, or initial commit.
4. Create a separate clean local repository from the verified tracked snapshot. Do not reuse or rewrite the source repository's `.git` history.
5. Create one root commit with the canonical author, committer, and subject.
6. Push the clean `main` branch to the new repository.
7. Create and push the annotated `v1.0.0` tag.
8. Publish a GitHub Release for `v1.0.0` with concise Chinese release notes covering both analysis routes, seven roles, single-document output, evidence rules, and installation.
9. Verify the new repository and release before touching the legacy repository again.

The source local checkout remains available until migration completion. Its remote may temporarily point to the legacy repository during migration, then must be updated to the new repository URL after verification.

## Verification Gates

Before the clean root commit:

- `python -m unittest discover -s tests -v` passes.
- `python -m compileall -q skills tests` exits 0.
- `git diff --check` exits 0.
- Active files contain `1.0.0` and do not present `0.3.0` as the current version.
- The installable directory is only `skills/summarizing-internship-work`.

After pushing the new repository:

- The default branch is `main`.
- `main` contains exactly one commit before release metadata generated by GitHub.
- The root commit author and committer resolve to `zhengguojie0922-crypto`.
- The `v1.0.0` tag resolves to the root commit.
- GitHub Actions completes successfully.
- README installation URLs resolve to the new repository.
- The GitHub Release is publicly visible.
- The Contributors graph contains no commit attributable to `zgjaaaaaa`; GitHub may require time to recompute the display.
- A fresh installation can locate `skills/summarizing-internship-work/SKILL.md`.

## Legacy Deletion Gate

Permanent deletion is the final action and is not part of initial migration setup. Before deleting `internship-work-summary-skill-legacy`, resolve and display the exact owner/repository target and verify all post-push gates. Obtain action-time confirmation for the permanent deletion even though this design is approved.

Deleting the legacy repository permanently removes its Stars, Issues, pull requests, Actions history, settings, and old repository redirect. Do not delete it when any verification gate is incomplete, GitHub is still processing the new repository, or the new repository cannot be independently installed.

## Failure and Recovery

- If local v1.0 verification fails, fix the release branch before any GitHub rename.
- If the legacy rename succeeds but new repository creation or push fails, keep the legacy repository and restore its original name if necessary.
- If the new repository exists but validation fails, repair or recreate the new repository while the legacy repository remains intact.
- Never delete the legacy repository as a way to resolve a naming, authentication, contributor-cache, or CI problem.

## Out of Scope

- Rewriting the existing repository history in place
- Preserving old Stars, Issues, pull requests, Actions runs, or contributor statistics
- Changing feature tracing, Git discovery, supported roles, output structure, or evidence rules
- Importing, forking, mirroring, or using GitHub Importer for the new repository

## Acceptance Criteria

The migration is complete when `zhengguojie0922-crypto/internship-work-summary-skill` is a public repository with one clean root commit, a passing `main` branch, a public `v1.0.0` release, working installation guidance, and no Git history attributable to the previous account. The legacy repository may be permanently deleted only after these conditions are independently verified and the exact deletion receives action-time confirmation.
