# Internship Work Summary Skill

`summarizing-internship-work` 从本地代码库和 Git 证据总结可核验的实习产出，并生成简历和面试准备文档。当前版本为 `1.1.0`，采用 MIT 许可证。

## 快速安装

在 Codex 对话中执行：

```text
使用 $skill-installer 从 https://github.com/zhengguojie0922-crypto/internship-work-summary-skill/tree/main/skills/summarizing-internship-work 安装这个 Skill。
```

也可以使用 Skills CLI；Node.js 只用于安装器，Skill 运行时只使用 Python 标准库。

```sh
npx skills add zhengguojie0922-crypto/internship-work-summary-skill --skill summarizing-internship-work --agent codex --global --yes
npx skills add zhengguojie0922-crypto/internship-work-summary-skill --skill summarizing-internship-work --agent claude-code --global --yes
```

Windows PowerShell 使用相同参数的 `npx.cmd skills add` 命令。安装后在新对话中调用 `$summarizing-internship-work`。

## 详细功能

- **功能代码链路追踪**：从自然语言描述的功能出发，沿入口、页面或接口边界、业务逻辑、数据流、持久化、依赖、配置、异常处理和测试逐层追踪。用户要求把命名功能写入个人简历、实习总结或个人产出时，默认该功能由用户完整实现，并把这一归属记为用户提供的证据；仅要求分析功能实现时，不自动声明个人所有权。
- **Git 实习产出发现**：在未指定功能时，先发现并确认 Git 身份和目标岗位，再按完整姓名或完整邮箱精确匹配主作者及共同作者提交，将相关改动聚类为业务或工程产出并补齐实现链路。身份别名需要逐个确认，不做子串匹配或自动合并。
- **证据与归属边界**：区分源码事实、Git 归属、用户补充和分析推断；命名功能个人产出采用用户提供的归属，Git 发现路线采用提交证据，协作者代码只用于解释上下文。
- **简历表述**：为每项主要产出生成保守版、标准版和影响力版三种写法，并按目标岗位调整技术重点。
- **面试准备**：生成 30 秒、1 分钟和 3 分钟介绍；每项主要产出附约 20 个核心问题、简洁参考回答、可能追问和回答方向，并另附 3-5 个独立场景题。证据不足时少于 20 个，不为凑数编造内容。
- **单文档输出**：分析笔记只保留在上下文中，运行时仅写入 `career-output/实习产出与面试准备.md`，不创建中间文档或中间目录。文件已存在时更新对应产出并保留无关的已验证内容，只有用户明确要求重建时才整体替换。
- **安全与真实性**：只读检查仓库，不运行目标代码或安装依赖；不编造指标、业务结果或所有权，并对秘密、个人信息和内部地址脱敏。

### 支持的目标岗位

| 目标岗位 | 重点追踪的代码证据 | 简历与面试输出重点 |
|---|---|---|
| 前端（`frontend`） | 页面入口、组件层级、状态管理、接口调用、交互、性能与前端测试 | 用户流程、组件设计、状态一致性、体验与性能取舍 |
| 后端（`backend`） | 路由、控制器、服务、领域逻辑、数据访问、事务、权限、异常与测试 | API 设计、分层架构、数据一致性、性能、安全与可靠性 |
| 客户端（`client`） | 页面或视图、状态模型、网络层、本地存储、生命周期、平台适配与测试 | 客户端架构、状态同步、弱网与离线处理、稳定性和性能 |
| 测试（`testing`） | 测试用例、fixture、自动化框架、CI、覆盖范围、缺陷与回归链路 | 质量策略、风险识别、自动化建设、缺陷定位与发布保障 |
| DevOps | CI/CD 工作流、构建部署脚本、容器与环境配置、监控、权限和回滚 | 交付流程、环境一致性、可观测性、可靠性与安全边界 |
| 数据分析（`data analytics`） | 数据采集、清洗、SQL、指标口径、数据模型、可视化与质量校验 | 数据链路、指标设计、分析方法、数据质量与可验证业务价值 |
| 算法（`algorithm`） | 数据预处理、特征、模型、训练、评估、推理、实验和性能优化 | 算法选择、实验设计、效果评估、性能权衡与工程落地边界 |

## 触发与路由

用户提到“实习产出”“实习总结”“项目经历”“简历包装”“把某个功能写到简历”“面试准备”等意图时，Skill 可以隐式触发；也可以显式调用 `$summarizing-internship-work`。

Skill 根据请求中是否包含具体功能和个人归属需求选择路线：

| 请求信号 | 采用路线 | Git 身份处理 | 分析重点 |
|---|---|---|---|
| 明确功能，并要求写入个人简历、实习总结或个人产出 | 命名功能路由 | 不询问 Git 身份 | 默认该功能由用户完整实现，以用户陈述作为归属证据，直接追踪代码链路 |
| 明确功能，但只要求分析实现 | 命名功能路由 | 不询问 Git 身份 | 追踪完整代码链路，但不自动声明个人所有权 |
| 未指定功能，只要求总结实习产出或工作成果 | Git 发现路由 | 请求未明确提供时，同时确认 Git 身份和目标岗位 | 用完整姓名或完整邮箱精确匹配主作者和共同作者提交，再追踪对应实现 |
| 明确功能，并明确要求 Git 校验归属 | 混合请求 | 需要时确认 Git 身份 | 先追踪功能，再用 Git 校验个人归属证据 |

确认遵循以下规则：

- 先从请求和仓库证据推断仓库、功能、范围、语言和目标岗位，减少用户输入。
- 所有关键缺失信息合并成一个问题，整个过程确认最多两轮。
- 命名功能路由不询问 Git 身份；Git 发现路由如果请求没有明确给出 Git 身份或目标岗位，会在分析提交前用同一轮问题确认两者。
- 命名功能的个人产出请求不因代码作者不同而降级；只有用户明确要求 Git 校验时才进入混合请求。
- 第二轮后不再设置审批门槛；可选信息缺失时继续分析，并在最终文档中明确标为未知或“用户未确认”。

典型请求：

```text
帮我把订单退款功能写到后端实习简历里，并准备面试问题。
根据这个仓库的 Git 提交总结我的实习产出，目标岗位是前端。
```

## 输出文档

运行时仅创建当前可写工作区中的最终文档 `career-output/实习产出与面试准备.md`，必要时只创建它的父目录。即使可写工作区也是被分析仓库，该文档也是唯一明确允许的工作区写入；仓库源文件和 Git 状态保持只读。不会创建中间 JSON、evidence、fact-card、audit 或 session 文件，也不会创建其他中间目录。

默认选择证据最强的 3 项主要产出；明确要求全面总结时才扩展到最多 5 项。最终文档已存在时，只更新匹配的产出并保留无关的已验证内容；只有用户明确要求重建时才整体替换。

每个主要产出包含：

- 业务功能和可证实的用户价值，以及完整代码路径。
- 三种简历表述，均贴合目标岗位。
- 30 秒、1 分钟和 3 分钟面试自我介绍。
- 每个主要产出约 20 个核心问题、简洁参考回答、可能追问和回答方向，另附 3-5 个独立场景题；证据不足时少于 20 个，禁止凑数。
- 需要用户补充的指标，以及证据索引、归属边界和置信度。

支持 `frontend`、`backend`、`client`、`testing`、`DevOps`、`data analytics`、`algorithm` 岗位，并支持中文、英文和双语输出。

## 安全边界

仓库检查始终只读，不执行目标仓库代码、构建、测试、安装器或生成命令。文档不编造指标、规模、因果关系或业务结果，也不推断用户未声明且没有 Git 证据的个人归属；缺少依据的指标会标记为需要用户输入。输出会脱敏秘密、凭据、个人信息、私有地址和专有内容。
